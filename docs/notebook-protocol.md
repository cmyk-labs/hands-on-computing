# Jupyter Notebook 编写协议

## 适用范围与规则归属

本协议适用于所有教学 Notebook，包括本地草稿；编写、修改或验收前必须读取并遵守。

本文件保存通用的 Notebook 写作与验收要求。[AGENTS.md](../AGENTS.md)规定项目范围、知识来源和依赖管理原则；代码写法按实际语言读取[对应编程规范](../AGENTS.md#编程规范)，包括随章辅助代码。环境配置见所属技术目录的 README.md；技术专属的展示、排版与检查要求见该目录 AGENTS.md。编写前一并读取，专属要求在其范围内适用，用户最新明确要求优先。

## 节点与教学组织

- 一份 .ipynb 围绕一个明确的章节主题，可以包含服务于同一主要学习目标的多个相关知识点。按学习关系划分章节，不固定文件数量，也不把每个术语或例子机械拆成一篇。
- 从具体用途和小例子引入，先讲基本用法，再说明必要机制与边界；多个独立学习目标或过长的前置知识链需要拆章。基础章不强制加入底层原理、手算、图表或性能实验。
- Notebook 是该章唯一的教学正文，目录 README.md 只提供范围说明或运行入口。多文件包、命令行、服务等主题可配套必要源码，完整项目归 projects/。
- 必需的配套脚本及其资源统一放在 Notebook 所属技术目录的 scripts/章节/ 下，章节目录使用二位序号与英文小写 kebab-case，例如 scripts/08-modules-and-packages/；可导入的模块和包仍使用 snake_case。仅在实际需要时创建，不建立空目录或占位脚本；检查结束后及时清理临时脚本和临时运行产物，保留教学所需文件。
- 文件名采用“二位章节序号-规划表中的章节名称.ipynb”，例如 01-基础语法.ipynb；一级标题为“基础语法”。按章节编写时直接放在技术目录，不为单章增加重复分类层级；可导入的 Python 模块和包仍使用 snake_case。
- 先在本地草稿中确认基础样板，再逐篇展开；通过来源核查与实际验证后，按任务要求整理到正式目录。

## 每篇 Notebook 的结构

| 位置 | 编写要求 |
| --- | --- |
| 开篇 | 第一个 Markdown 单元使用唯一的一级标题，依次单列“学习目标：”和“前置知识：”，再简述适用版本和必要运行条件；“环境准备：”链接到本技术目录 README.md；有配套文件时补充“配套脚本：”及用途清单 |
| 主知识点 | 使用连续编号的二级标题，如“## 1 数值类型”；标题写具体内容，不用“知识点”代替名称 |
| 必要的子知识点 | 使用“### 1.1 整数”等三级标题，仅在有独立讲解与观察目标时拆分；通常不继续增加 1.1.1 等层级 |
| 讲解与代码 | 默认简短讲解后紧接一个可执行 Code 单元；具体展示与运行方式遵循对应技术目录的补充规则 |
| 组织性标题 | 二级标题若只是多个子知识点的共同入口，可只写必要导语，不强加代码；避免只有层级作用的空标题 |
| 结果说明 | 预期结果、检查方法和结果解释写在对应代码注释中，实际输出由执行生成；代码后不另加结果说明单元 |
| 本章小结 | 使用“## 本章小结”，归纳关键要点与理解自查，不重复全文 |
| 练习 | 使用“## 练习”，写明任务、可验证标准及必要提示；答案或提示与题目分开 |
| 参考与引用来源 | 使用“## 参考与引用来源”，作为最后一个单元，按网站汇总实际核查的来源 |

本章小结、练习和参考与引用来源不参与知识点编号。Notebook 不编写“验证记录”和“核对内核”部分，不添加专门打印解释器路径或环境信息的代码单元；实际检查结果只在当次交付说明中报告。

### 开篇写法

- “学习目标：”用一句话概括学完本章能理解什么、完成什么操作，与实际正文对应，不重复罗列章节目录，也不把尚未编写的内容列为已覆盖目标。
- “前置知识：”简述所需概念或操作，例如“变量赋值、容器操作、解包”，不用“先修第 X～Y 章”或章节编号代替知识说明。没有专门要求时直接写明，例如“无需编程基础”。
- 环境准备只链接到所属技术目录 README.md；安装工具、创建环境和安装整套课程依赖的步骤集中维护。章节保留实际版本条件、工作目录、输入、运行命令及关闭方法，不重复完整准备流程。
- 配置与运行按“Step 1：一句话说明 → 一个命令块”列出，一步只做一件事；界面操作写一句具体操作。条件紧邻对应步骤，不把多个命令、分支和长段解释挤在同一步。首次准备和日常运行按需分开。
- 环境管理、编译、打包等本身属于章节学习目标时，保留对应教学讲解和示例；不因安装步骤集中到 README.md 而删除知识点。
- 有必需的配套文件时，在头部写“配套脚本：位于 scripts/章节/”，路径相对于 Notebook；随后用简短编号列表列出实际文件或目录及教学用途，并提供相对链接。没有配套文件时省略此项；文件移动或改名后同步更新头部、正文链接、代码路径和命令示例，并重新检查受影响的代码或浏览器操作。
- 头部、正文和命令中的项目内路径写成完整的相对路径。代码中的固定路径也放在一个字符串内；有变量时只连接完整固定后缀，不逐级拆分目录名称。课程路径写法和起点说明见对应技术目录 AGENTS.md；Markdown 链接使用正斜杠，路径中的下划线转义不得带入实际文件名。

### 讲解与措辞

- 用熟悉、具体的词说明用途和行为，再引入必要术语。避免一段集中引入多个未解释的概念；必须提前使用后文工具时，先简述当前用途并准确指向后文。
- 采用通行专业译法，对照官方或第一方原文确认含义，不自创术语或逐词硬译，也不把某一份官方中文译文视为唯一正确译法。易歧义、译名不统一或不直观的术语首次附英文原名，同一概念前后保持一致。
- 库名、API 和工具名称保留原文，必要时附简短中文含义或用途，不强行另造中文名称。
- 同一对象属于不同分类，或同一概念在不同章节出现时，如容易混淆，用一句话说明分类关系或本章侧重点，例如“list 既是 Python 内置类型，也属于容器”；不重复展开已有讲解。
- 写法或公式中的 x、y、n 等占位符首次出现时就地说明所指对象；必要时写明类型、取值范围、单位或维度。说明紧邻公式或表格，不让读者从后文代码猜测。
- 保留有助于区分语法的操作数。例如 +x、-x 中，x 代表参与运算的数值；应解释 x 的含义，并用具体数值示例说明写法，不直接删去 x。表中只列运算符时，也应另给完整写法或示例。
- 删除重复导语、写作流程、无关抽象概念，以及对代码和注释的重复复述；保留必要条件、易错边界和相似概念之间的区别。

### 阅读与排版

- 一个自然段围绕一个意思，用空行区分用途、基本规则和易错边界，不堆成长段，也不逐句硬换行。同一知识点的分段留在同一个 Markdown 单元内。
- 多个并列规则可列项，默认用中文括号编号“（1）”“（2）”，也可用“①”“②”；同组格式一致，每项单独成段，不为一两个短句机械列项。
- 类型、术语或 API 总览表保留原文名称，并增加“中文名称／含义”列；每个独立项目一行、一一对应，例如 set 对应“集合”，frozenset 对应“不可变集合”。用途、可变性、示例等列按当前主题选择，不将多个需要分别解释的名称合并在一格。
- 去掉单元首尾空白行，篇末不追加空单元。代码能清楚写在一行时不人为拆行，语法要求或演示续行除外。
- 使用标准 Markdown 与代码单元，不依赖自定义字体或 CSS。正文中的术语、名称与短代码使用普通文字，不用反引号生成行内高亮；Markdown 特殊字符按需转义，确保符号和表格正确显示。
- 减少重复的“问题、官方说明、依据、成功标准”等标签。来源核查、单元编排和验收过程不写进教学导语；必要的节译说明可在开篇统一标明，引用块只用于明确标识的摘录或节译。

## 最小代码与注释

- 每个代码单元承担一个清楚的观察目的，高度相关的现象可合并观察。使用小型输入和直接写法，不为格式添加无关类、配置层、包装函数或未介绍的高阶语法。
- 教学单元可直接写表达式和语句，用 print() 或单元结果展示观察，不机械套用 main() 入口；配套脚本仍遵守脚本规范。需要由内核运行的教学代码放在 Code 单元执行，不能只贴在 Markdown 代码块中。
- 保留有信息量的中文注释，解释输入、关键原因、边界、预期结果及检查方法，不逐行翻译语法。多步骤代码可用“# 1.”“# 2.”标明阶段；单一操作不强行编号。修改代码时同步更新注释和 docstring。
- 输入尽量就地给出；依赖前文导入或定义时明确说明，不能依赖其他 Notebook 或历史执行遗留的隐藏状态。
- 反例只在有助于理解重要边界、常见误解或实际风险时保留。普通语法错误可简述，不为证明简单错误提前引入测试框架、动态执行等高阶机制。
- 可执行反例须明确说明预期异常或错误结果，验证预期失败并保证整篇仍可顺序执行；不能忽略所有错误来掩盖真实失败。
- 练习不能用无条件报错的占位代码阻断运行。检查围绕学习目标，不照抄实现；预测输出题不在待预测语句旁直接写答案，可注明运行后如何核对。

## 环境与执行

- 含 Code 单元的 Notebook 在运行前确认所需内核可用，并按所属技术目录 README.md 准备环境；Python 课程沿用 hands-on-computing Conda 环境。解释器归属只在执行检查时核对，不写成教学单元。纯 Markdown 章节按技术协议运行配套文件。
- 依赖清单使用对应技术的格式并集中到技术目录：pip 依赖使用 requirements.txt，npm 依赖使用 package.json 和锁文件。没有相应依赖就不创建清单，不为每章分散创建同类清单或独立环境。
- Code 单元从空内核自上而下执行，写明必要工作目录与输入文件。涉及服务、模型下载、账号或外部资源时，写明运行条件、资源需求、可能费用及关闭清理方法。
- 随机实验记录种子并说明必要的硬件或后端差异；模型实验注明模型标识与修订版、数据版本、关键参数和评估方法。模拟观察不替代真实服务或模型的验证。
- 保存的输出与执行计数必须来自实际运行。代码、依赖或输入变化后重新验证，不能把旧输出当作新版本通过的证据。
- 只有执行并检查结果后才能报告运行通过；未执行、失败或只检查了部分内容时如实说明。安装、语法检查、文档构建和实验执行分别报告。

## 参考与引用来源规则

- 每个知识点写作前核查直接支持其内容及适用条件的官方或第一方来源，定位到页面、小节、版本、论文页码或源码位置；代码注释中的知识解释同样需要依据，不能凭记忆或推测补写。
- 正文知识点后不放来源链接，统一汇总到篇末。只列实际核查且确实支持本章的资料，不列计划阅读的网站，也不为此下载、复制或另建来源归档。
- 最后一个单元固定为“## 参考与引用来源”，其后不追加代码或练习。一个网站只列一次，合并该站点支持的多个知识点与页面，保留直接链接及必要定位；不能只给首页让读者自行搜索。
- 按实际文档站点分组，不把独立站点混成同一来源；同一托管网站上的不同项目或论文合并在一条记录中，但保留各自名称、位置与用途。涉及多个版本时说明对应关系。
- 摘录或节译明确标识，忠实于来源并遵守授权，不整篇搬运。来源无法核实时暂不写入正式正文，在当次交付说明中指出缺口。

## 章节验收

- 主题和标题层级清楚；头部有简洁的“学习目标：”和“前置知识：”，前置知识写具体概念或操作；讲解与最小代码相邻，小结、练习及参考来源齐全。
- 必需的配套文件位于 scripts/ 对应章节目录，头部的路径和用途清单与实际文件一致；引用可访问，无遗留临时脚本或临时运行产物。
- 段落简短而完整，术语前后一致，总览表的原文名称与中文含义逐项对应，符号首次出现有解释；必要边界与练习指向准确。
- 知识解释及代码注释可追溯到写作前核查的来源；篇末来源按网站去重，链接定位直接支持相应内容。
- 实际输出、预期行为与检查结果明确区分；Code 单元从空内核顺序执行通过，反例和练习不阻断运行；浏览器示例检查实际页面及交互。
- 不含验证记录、内核核对或空单元；交付时报告实际执行范围、结果及未验证事项，不另建 Notebook 验证记录文件。

## 本协议的教学组织参考

问题驱动、小型示例、逐步实现与结果观察的组织方式参考 [Modern LLM Notebook](https://github.com/walkinglabs/modern-llm-notebook) 和其中的 [Tokenizer 示例](https://github.com/walkinglabs/modern-llm-notebook/blob/main/notebooks/part1-foundation/01-tokenizer-basics.ipynb)。这里借鉴教学方法，不将其作为 Python 语言规则的权威依据，也不直接复制课程正文或代码。
